# ADR-004 — RLS: хэрэглэгчийн client зөвхөн уншина

**Төлөв:** Батлагдсан · **Огноо:** 2026-10-19 · **Холбоос:** [backend_schema.md §1, §4](../backend_schema.md), [security.md §3](../security.md), audit C-01, C-03, C-08

## Нөхцөл

Supabase-ийн нийтийн (anon) түлхүүр browser-т ил байдаг тул нэвтэрсэн хэрэглэгч PostgREST-ийг шууд дуудаж чадна. Анхны санал болгосон `for all` policy нь хэрэглэгчид өөрийн мөрөө шууд бичих эрх олгож, серверийн бүх дүрмийг (уртын хязгаар, ээлж, квот, төлөвийн шилжилт, үгийн төлөв) тойрох боломж өгч байсан. Мөн хүснэгт хооронд өөр хэрэглэгчийн мөр рүү заах FK-г юу ч хориглоогүй.

## Шийдвэр

- `public` schema-ийн **бүх** хүснэгтэд RLS асаалттай. CI-д RLS асаагүй хүснэгт байгаа эсэхийг SQL-ээр шалгана.
- `authenticated` role-д хэрэглэгчийн хүснэгт дээр зөвхөн `select` policy (`user_id = (select auth.uid())`). `insert`/`update`/`delete` policy үүсгэхгүй. `anon`-д policy байхгүй.
- Агуулгын хүснэгт: `select` (`is_active`). `ai_usage_events`, `usage_counters`: policy байхгүй.
- Уншилт серверт `src/lib/supabase/server.ts` (хэрэглэгчийн session-тэй client)-ээр — RLS идэвхтэй.
- Эцэг-хүүхдийн эзэмшлийг composite FK (`(parent_id, user_id) references parent (id, user_id)`) баталгаажуулна; эцэг хүснэгт бүрт `unique (id, user_id)`.
- RLS-ийг хоёр тест хэрэглэгчээр, API-гаар болон anon түлхүүртэй client-ээр шууд тестлэнэ.

## Үр дагавар

- Бүх бичилт серверээр (ADR-005) — серверийн шалгалт заавал, тойрох боломжгүй.
- RLS нь уншилтын хамгаалалт болж үлдэнэ (серверийн кодын алдаа өөр хэрэглэгчийн өгөгдлийг уншуулахгүй).
- Browser-ийн Supabase client зөвхөн нэвтрэлтэд (OTP) ашиглагдана.
- 3-р шатны багшийн самбар нэмэлт `select` policy-оор өргөтгөгдөнө.
- `(select auth.uid())` хэлбэр, Supabase-ийн default grant-ийг хэрэгжүүлэх үед шалгах шаардлагатай.
